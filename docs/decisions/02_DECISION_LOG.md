## DL-20260720-001 — GBDT 라이브러리를 XGBoost로 확정

- **상태:** 채택
- **작성일:** 2026-07-20
- **관련 문서:** TD-004 (모델)

### 배경

`04_TECHNICAL_DECISIONS.md`의 미확정 항목 중 "XGBoost와 LightGBM 중 선택"이 남아 있었습니다.

### 검토한 대안

1. XGBoost
2. LightGBM
3. scikit-learn `HistGradientBoostingRegressor`

### 최종 결정

**XGBoost를 GBDT 대표 모델로 사용합니다.**

### 근거

- 학습 샘플이 wafer-stage **1,981건**으로 GBDT 기준 소규모입니다.
- LightGBM의 leaf-wise 성장은 이 규모에서 과적합 경향이 있어 `min_data_in_leaf` 조정이
  사실상 필수입니다. XGBoost의 level-wise 성장이 기본값에서 더 안정적입니다.
- SHAP `TreeExplainer` 지원은 두 라이브러리가 동일하므로 P1 기능에 차이가 없습니다.
- 대안 3은 네이티브 의존성이 없다는 장점이 있으나, 아래 설치 문제가 해결되어 불필요해졌습니다.

### 영향 범위

- 변경 파일: `requirements.txt`, `pyproject.toml`
- macOS는 `brew install libomp` 선행 필요 (없으면 import 시 `libomp.dylib` 로드 실패).
  본 작업 환경에서는 설치 후 `xgboost 3.3.0` import 정상 확인.

### 남은 한계

Hyperparameter 범위는 아직 정하지 않았습니다. 2주차에 제한 탐색으로 결정합니다.

## DL-20260720-002 — Stage 분리 대신 STAGE + CHAMBER 계열을 조건 변수로 사용

- **상태:** 채택
- **작성일:** 2026-07-20
- **관련 문서:** `01_PROJECT_SOURCE_OF_TRUTH.md` 3장, TD-001

### 배경

"Stage A와 B를 하나로 합칠지 별도 모델로 나눌지"가 1주차 EDA 과제로 남아 있었습니다.

### 데이터 확인 결과

`scripts/01_profile_raw.py` 기준:

- 고유 wafer-stage **1,981건**, 라벨 1,981건과 **1:1 일치 (누락 0건)**, 총 672,744 row.
- `AVG_REMOVAL_RATE` 분포

  | 구분 | 건수 | 평균 | 범위 |
  |---|---|---|---|
  | Stage A 저구간 | 798 | 73.1 | 53.4 ~ 88.7 |
  | Stage A 고구간 | 368 | 195.4 | 138.6 ~ 4326.2 |
  | Stage B | 815 | 80.0 | 54.3 ~ 101.5 |

  Stage A는 88.7과 138.6 사이가 비어 있는 **이봉분포**입니다.

- `CHAMBER`는 wafer-stage 안에서 고정값이 아니라 **1→2→3** 또는 **4→5→6** 으로 순차 변합니다.
  두 계열은 섞이지 않으며, 계열이 Stage A의 이봉분포를 완전히 설명합니다.

  | CHAMBER 계열 | 그룹 수 | 구성 |
  |---|---|---|
  | `{1,2,3}` | 368 | Stage A 고구간 **전부** |
  | `{4,5,6}` | 1,613 | Stage A 저구간 798 + Stage B 815 |

### 최종 결정

**Stage A/B로 모델을 분리하지 않고, `STAGE`와 파생 변수 `chamber_group`(G123/G456)을
함께 조건 변수로 투입해 단일 모델로 먼저 학습합니다.** 시간순 validation에서 조건별
성능 격차가 크면 그때 분리 모델을 검토합니다.

### 근거

- 실제 구분선이 Stage가 아니라 CHAMBER 계열이므로, Stage만으로 나누면 서로 다른 두
  공정 조건이 Stage A 안에 그대로 섞입니다.
- 조건 변수로 넣으면 tree 모델이 분기를 스스로 학습할 수 있고, 샘플을 쪼개지 않아
  1,981건이라는 적은 데이터를 낭비하지 않습니다.
- 분리 모델은 조건별 성능 격차라는 근거가 확인된 뒤에 도입하는 편이 순서상 맞습니다.

### 영향 범위

- 변경 파일: `config/features.yaml`
- 변경되는 Feature: `chamber_group`, `chamber_dwell_time` 신규
- 원본 `CHAMBER`를 categorical feature로 직접 사용하지 않습니다.

### 검증 방법

시간순 validation에서 `chamber_group`별 MAE/RMSE를 따로 계산합니다. 한쪽 조건의 오차가
현저히 크면 이 결정을 재검토합니다.

### 남은 한계

`CHAMBER` 값이 물리적 챔버 번호인지 공정 하위 단계인지는 확인하지 못했습니다.
공개 데이터에 설명이 없으므로 **관측된 그룹 구분자**로만 사용하고, 물리적 의미를
보고서에서 단정하지 않습니다.

## DL-20260720-003 — MRR 극단 이상치 4건 제외 및 MACHINE_ID 제거

- **상태:** 채택
- **작성일:** 2026-07-20

### 배경

프로파일링 중 타깃과 컬럼에서 두 가지 문제가 확인되었습니다.

### 데이터 확인 결과

- `AVG_REMOVAL_RATE` 상위 4건: **4326.15 / 4202.11 / 4182.42 / 4129.49**
  (전부 Stage A, CHAMBER 계열 `{1,2,3}`). 5번째로 큰 값은 **162.64**로 약 26배 차이.
- `MACHINE_ID`는 672,744 row 전체에서 값이 `2` 하나뿐입니다.

### 최종 결정

1. **`AVG_REMOVAL_RATE > 1000` 인 4건을 학습·평가에서 제외합니다.**
2. **`MACHINE_ID`를 feature에서 제외합니다.**

### 근거

- 4건은 정상 분포와 연속되지 않는 완전 분리된 값이며, 물리적으로 설명되지 않습니다.
  포함 시 SPC 관리한계 계산이 이 4건에 지배당합니다.
- 상수 컬럼은 모델에 정보를 제공하지 않습니다.

### 영향 범위

- 변경 파일: `config/features.yaml`
- 학습 데이터: 1,981건 → **1,977건**
- 제외 건수가 4가 아니면 파이프라인이 중단되도록 검증을 넣습니다.

### 남은 한계

이 4건이 측정 오류인지 실제 이상 공정인지는 공개 데이터만으로 확정할 수 없습니다.
보고서에는 "제외한 이상값 4건"으로 명시하고 은폐하지 않습니다.
`STAGE B`의 row 수 최대 5,492(중앙값 347), 공정시간 최대 29,311초(중앙값 356초) 같은
그룹 단위 이상치는 **아직 처리하지 않았습니다.** 별도 결정이 필요합니다.

## DL-20260720-004 — 그룹 단위 이상치를 제거하지 않고 Feature로 흡수

- **상태:** 채택
- **작성일:** 2026-07-20
- **관련:** DL-20260720-003의 "남은 한계"에서 미결로 남겨둔 항목

### 배경

공정시간 최대 29,311초(중앙값 356초), row 수 최대 5,492(중앙값 342)인 그룹이 있어
이상치로 제거할지 판단이 필요했습니다.

### 데이터 확인 결과

| 구분 | 건수 | MRR 평균 | MRR 최대 |
|---|---|---|---|
| duration <= 500초 | 1,938 | 98.88 | 4326.15 |
| duration > 500초 | 43 | 87.32 | **152.25** |

- 공정시간이 긴 43건(2.2%)의 타깃은 **정상 범위**입니다. 오히려 전체보다 분산이 작습니다.
- duration 최대인 그룹(WAFER_ID 2921014258)은 `n_rows`가 353으로 중앙값 수준입니다.
  즉 센서 샘플 수는 정상이고, 중간에 큰 시간 공백이 있을 뿐입니다.

### 최종 결정

**제거하지 않습니다.** 대신 공정시간을 세 개의 Feature로 분리합니다.

- `duration_total`: last_ts - first_ts (공백 포함)
- `duration_active`: 연속 샘플 구간의 합 (공백 제외)
- `gap_max`, `gap_count`: 샘플 간격이 비정상적으로 큰 구간

### 근거

- 타깃이 정상이므로 "이상"이라고 볼 근거가 없습니다. 제거하면 근거 없는 2.2% 손실입니다.
- 공정 중단 자체가 pad·slurry 상태에 영향을 줄 수 있는 **정보**입니다. 버리는 대신
  명시적 Feature로 만들면 모델이 판단할 수 있습니다.
- `duration_total`만 쓰면 29,311이라는 값이 트리 분기를 왜곡합니다.

### 버린 대안

1. 43건 제거 — 타깃이 정상이라 제거 근거 없음
2. 상한 클리핑(예: 500초) — 정보는 버리면서 왜곡은 남음

### 남은 한계

공정 중단의 실제 원인은 공개 데이터로 알 수 없습니다. "샘플 간 시간 공백"이라는
관측 사실로만 기술합니다.

## DL-20260720-005 — 시간순 Split 경계에 buffer 구간 도입

- **상태:** 채택
- **작성일:** 2026-07-20
- **관련 문서:** TD-002 (데이터 분할)

### 배경

TD-002는 시간순 split을 규정하지만, wafer-stage 사이의 시간 구간 중첩 여부는
확인되지 않았습니다.

### 데이터 확인 결과

- `first_ts` 중복 0건 (정렬 기준으로 사용 가능)
- 그러나 **1,981개 중 870개(43.9%)** 가 직전 그룹의 `last_ts` 이전에 시작합니다.
  멀티 챔버 장비에서 여러 웨이퍼가 동시에 처리되기 때문으로 보입니다.

### 최종 결정

**`first_ts` 기준 정렬을 유지하되, train/validation/test 경계에 buffer 구간을 두고
경계에 걸쳐 시간이 겹치는 wafer-stage는 어느 split에도 넣지 않습니다.**

### 근거

- 단순 순번 분할을 하면 train 마지막 웨이퍼와 test 첫 웨이퍼가 실제로는 동일 시각에
  동일한 pad·dresser 상태에서 처리된 샘플일 수 있습니다. 이는 시간순 검증의 취지인
  "미래 구간 성능 추정"을 훼손합니다.
- scikit-learn 문서도 시간 의존 데이터에서 train/test가 과도하게 유사해지면 일반화
  성능 추정이 왜곡된다고 설명합니다.

### 영향 범위

- 변경 파일: `config/split.yaml`
- 제외되는 샘플 수만큼 학습·평가 데이터가 줄어듭니다. 실제 제외 건수를 기록합니다.

### 검증 방법

split manifest에서 각 구간의 `first_ts`/`last_ts` 범위가 서로 겹치지 않는지 확인합니다.

### 남은 한계

buffer 폭을 얼마로 둘지는 실제 중첩 길이 분포를 보고 정합니다. 과도하게 잡으면
학습 데이터가 줄어듭니다.
