# FabLens 개발 및 AI 작업 규칙

## 1. 기본 역할

이 프로젝트에서 AI는 다음을 돕습니다.

- 데이터 구조 분석
- 구현 단계 분해
- 코드 작성과 리뷰
- 실험 설계
- 오류 원인 추적
- 결과 해석
- README·보고서 정리

AI는 데이터에 없는 사실이나 실험 결과를 만들어내지 않습니다.

---

## 2. 작업 및 판단 우선순위

1. 실제 데이터와 실행 결과
2. 프로젝트 Source of Truth
3. 최신 Technical Decision과 Decision Log
4. 팀 역할과 일정
5. 심층 리서치 보고서
6. 일반적인 아이디어

기존 결정과 다른 방식을 제안할 때는 변경 이유와 영향 범위를 먼저 설명합니다.

---

## 3. 개발 요청에 대한 기본 출력

개발 단계를 요청받으면 다음 순서로 답합니다.

1. 이번 단계의 목표
2. 입력 파일과 확인할 데이터
3. 수정·신규 파일 목록
4. 구현 내용
5. 실행 명령
6. 검증 방법과 기대 결과
7. 실패 시 점검 항목
8. 다음 단계 진입 조건


---

## 4. 데이터 분석 규칙

- 실제 데이터 파일을 확인하기 전 컬럼을 확정하지 않습니다.
- row 단위 무작위 분할을 기본값으로 사용하지 않습니다.
- 동일 wafer-stage가 여러 Split에 섞이지 않게 합니다.
- 타깃 또는 미래 정보를 포함한 누설성 Feature를 점검합니다.
- 전처리 전후 row 수, wafer-stage 수, 누락 수를 기록합니다.
- 결측값을 무조건 평균으로 채우지 않고 발생 구조를 먼저 확인합니다.
- 식별자 컬럼은 모델 Feature와 추적용 Metadata를 구분합니다.
- 시간 정렬 기준이 불명확하면 임의로 순서를 만들지 않습니다.

---

## 5. 모델링 규칙

- 먼저 단순 Baseline을 완성합니다.
- 모델 성능보다 Split과 Feature의 타당성을 먼저 검토합니다.
- 대표 성능은 시간순 test 결과로 기록합니다.
- Hyperparameter 탐색은 제한된 범위에서 수행합니다.
- Test set을 보며 Feature와 파라미터를 반복 조절하지 않습니다.
- 성능이 기대보다 낮아도 데이터를 조작하거나 평가 구간을 바꾸지 않습니다.
- Seed와 라이브러리 버전을 기록합니다.

---

## 6. SPC 규칙

- 관리한계와 제품 규격을 혼동하지 않습니다.
- Phase I 기준 구간으로 관리한계를 만들고 Phase II에서 적용합니다.
- 기준 구간이 안정적이라는 근거를 확인합니다.
- holdout 실제 MRR은 평가용이며 실시간 판정 입력으로 사용하지 않습니다.
- ‘이상 웨이퍼’는 프로젝트 내부 통계적 정의임을 명시합니다.
- EWMA·CUSUM은 기본 관리도 완료 후에만 제안합니다.

---

## 7. SHAP 규칙

- SHAP 결과를 ‘원인’이 아니라 ‘예측 기여도가 큰 원인 후보’라고 표현합니다.
- 상관된 Feature가 있을 때 개별 변수 해석을 과신하지 않습니다.
- 전역 중요도와 개별 wafer-stage 설명을 구분합니다.
- Feature 이름이 센서와 Stage를 추적할 수 있게 유지합니다.

---

## 8. 범위 통제

다음 기능을 먼저 제안하지 않습니다.

- Conformal Prediction
- Adaptive SPC
- OOD
- FastAPI
- 별도 DB
- Digital Twin
- LLM·RAG
- 딥러닝
- 공정 자동 제어

P0와 P1이 완료되고 테스트가 통과한 경우에만 확장 후보로 검토합니다.

---

## 9. 코드 품질 기준

- 경로와 설정값을 코드에 반복 하드코딩하지 않습니다.
- 데이터 처리, Feature, 모델, SPC, UI를 모듈로 분리합니다.
- 함수 입력·출력과 타입을 명확히 합니다.
- 중간 산출물 Schema를 문서화합니다.
- 최소한 핵심 변환과 Rule Engine에 테스트를 작성합니다.
- Notebook에서 검증한 로직은 최종적으로 `src/` 모듈로 이동합니다.
- 결과 파일을 덮어쓸 때 실험 ID 또는 timestamp를 사용합니다.

## 11. 금지되는 과장

- 실제 Fab에서 검증했다고 쓰지 않습니다.
- 실제 수율 또는 비용을 개선했다고 쓰지 않습니다.
- 불량 원인을 확정했다고 쓰지 않습니다.
- 검사를 대체했다고 쓰지 않습니다.
- 구현하지 않은 확장 기능을 완료 기능처럼 쓰지 않습니다.
